# Results: 25 Neural Skill Transplantation

**Question:** two HalfCheetah policies with the same architecture and the same observation/action
conventions learn opposite skills: run forward (`fwd`) and run backward (`bwd`). Both branch from
one shared start θ0. Can they be combined into one task-conditioned network without retraining
everything?

**Short answer (4 training seeds, 10 held-out eval episodes each):**

* **Training-free weight merging failed.** With shared pretraining, every merge (averaging, task
  arithmetic, TIES, DARE, λ tuned on validation seeds) is *no better than the shared start θ0 it
  branched from*. With the original λ grid (≥ 0.3) they are worse (25–39% vs θ0's 45% mean retained). The validation search, given λ down to 0, picks λ ≈ 0, which means "don't add
  the task vectors". With only a shared random init, merges score about 0% of the specialists.
  This is a clear negative result for this conflicting pair.
  *Review addition:* the trivial "one specialist for both labels" network also beats every merge.
  The fwd specialist run under both labels keeps **56% ± 7** mean retained, picked on validation
  seeds by mean retained in 4/4 seeds. Per seed it is ahead of θ0 by +0.2 / +0.8 / +21 / +18 points
  (a tie in two seeds) and ahead of every merge except extended-grid DARE in seed 1 (−2.7). Picked by the merges' own criterion
  (summed raw validation return) it keeps 50% ± 7. In `init` it keeps 17% vs ≤ 3% for any merge
  (`results/review_checks.json`). So no merge beats running one of its own inputs, as on the
  compatible pair.
* **Distillation worked, and cheaply.** DAgger distillation of the two specialists into one network
  recovers **99% (pre) / 100% (init)** of the oracle switch on both tasks. It crosses 90% on both
  tasks by the **53k-step evaluation** (median; 78k for `init`; evals sit at 29k / 53k / 102k / 201k,
  so the true crossing lies between grid points). That is about 650 gradient steps (2.4k for the full
  200k) and uses no rewards.
  *Review correction:* "78k" is a median between grid points. Per seed, the first eval at ≥ 90% on
  both tasks is 53k / 29k / 102k / 53k (`pre`) and 201k / 102k / 53k / 53k (`init`): 3/4 seeds by
  53k and 4/4 by 102k in `pre`, 2/4 by 53k and 4/4 by 201k in `init`.
  *Review addition, matched total budget:* distillation is cheap only once the specialists exist.
  Counting their cost, the whole route is 0.5M + 2 × 2M + 0.2M ≈ 4.7M env steps for 99% / 100%
  (4/4 seeds ≥ 90% on both; 4.2M in `init`). Multitask PPO from scratch with 4.5M steps ends at 85% / 101% (2/4 seeds
  ≥ 90%). The 13–19× figure below counts post-specialist steps only (DAgger vs PPO fine-tune). At a
  matched total budget the margin over multitask-from-scratch is modest: 4/4 vs 2/4 seeds at 90%.
* **A merge is a poor policy but a useful starting point.** Multitask PPO fine-tuning started from
  the *averaged* weights beats the same fine-tuning started from θ0, in both conditions (1M steps:
  77% vs 68% mean retained in `pre`, 85% vs 54% in `init`). The average scores 25% and −5% as a policy.
* **Transfer between the two skills is negative.** The backward specialist is a worse starting point
  for learning forward than θ0 is (992 vs 4287 return after ~0.88M steps).
* **The scripted CPG gait** (3676 fwd / 4372 bwd, 61% mean retained) beats every training-free
  merge on fwd and on mean retained, and beats the averaging floor on both tasks. On bwd it sits
  below θ0 (4797) and the task-arithmetic/TIES merges (4942/5087).
  *Review update:* that search ended on its own box edge (f = 4.0 Hz, the upper bound, for both tasks)
  and the bwd elite curve was still rising. Re-tuned in a wider box with 2 CEM restarts
  (`cpg_wide.py`, training seeds only), the CPG scores **4075 fwd / 4693 bwd = 68% mean retained**
  (61% → 68%). It still sits just below θ0 on bwd, and it now beats every merge and the
  single-specialist network (56%) on mean retained.
* **Follow-up, compatible pair (fwd vs low-energy cruise):** here merging *does* work. With shared
  pretraining, the plain average keeps 76% of both specialists (θ0 alone: 39%). The interpolation
  path has no barrier, and the task vectors help each other instead of interfering. Still, no merge
  beat simply running the cruise specialist under both labels (86%). Merging only works as far as
  the skills are compatible.

All numbers below come from `results/summary.md` (generated by `report.py` from `results/*.json`)
unless a different file is named.

## Setup in one paragraph

`HalfCheetah-v5`, 1000-step episodes. Rewards: fwd = +v − 0.1|a|², bwd = −v − 0.1|a|². The policy
input is [normalized obs, task one-hot]. Actor and critic are separate tanh MLPs 19→128→128, the
action mean is tanh-bounded, and the normalizer is frozen after the base phase. The `init`
condition reuses the normalizer frozen from the same seed's `pre` base, so every branch shares one
input convention. This leaks a little pretraining information (17 means and variances) into `init`. PPO is in MLX with
numpy rollouts: 16 envs × 256 steps, 10 epochs, minibatch 1024, lr 3e-4 annealed, γ 0.99, λ 0.95,
clip 0.2. There are two shared-start conditions:
**`pre`**: θ0 = 0.5M steps of multitask PPO (8 fwd + 8 bwd envs).
**`init`**: θ0 = the same random init. Each specialist is PPO from θ0 on its own task for 2M env
steps; snapshots at 125k, 250k, 500k and 1M give the branch-length study. Training seeds 0–3 differ
in init, envs and PPO noise. Every return is the deterministic (mean-action) return on 10 held-out
reset seeds (10000–10009). Merge hyperparameters (λ) are chosen only on 5 validation reset seeds
(20000–20004), by the summed return over both tasks.

Wall-clock (busy machine, under load): the train stage (4 seeds × 8.5M steps + evals, 4

4-worker train job it ran at ~7.4k steps/s per worker at load average 20–36, because up to seven
builders were sharing the Mac. All throughput numbers are under load.

(method − θ0) / (specialist − θ0): the share of what each branch learned *after* the shared start
that survives the combination. In `pre` this is the honest metric, because θ0 already earns 45% by
itself. Mean ± std over 4 training seeds.

Without shared pretraining, the averaged network **ignores the task label**: it runs backward

## 2. Interference

**Within merges** (task arithmetic at the selected λ, `results/summary.md` "Interference"):

| condition | task | θ0 + λ·τ_own | θ0 + λ·(τ_fwd + τ_bwd) | drop from adding the other skill's vector |
|---|---|---|---|---|
| pre | fwd | 1382 ± 888 | 781 ± 782 | 601 ± 1144 |
| pre | bwd | 5745 ± 121 | 4942 ± 245 | 803 ± 255 |
| init | fwd | 3139 ± 1054 | −2111 ± 789 | 5249 ± 1798 |
| init | bwd | 5773 ± 1410 | 2218 ± 317 | 3555 ± 1287 |

In `pre`, even the forward task vector *alone* at λ = 0.3 lowers forward return below θ0
(1382 vs 1643). The forward skill is not a direction you can walk part-way along.

**During specialization (forgetting through shared weights):** the fwd specialist is trained only
with the fwd label. The `a1` weight column for the bwd one-hot gets exactly zero gradient, so the
two task vectors never conflict on the label columns, only on the shared hidden weights. Even so,
the bwd skill θ0 had (4797) falls to 897 ± 1111 after fwd specialization, and the bwd specialist
takes θ0's fwd skill from 1643 to −552 (`media/training_curves.png`, dashed lines). The task label
does not protect the other skill. Seed 3's fwd specialist kept 2189 on bwd at its last training eval
(`results/train_s3.json`), so the amount of forgetting varies by seed.
*Review check:* the zero-gradient claim holds exactly. In all 16 specialists (4 seeds × 2 conditions
× 2 tasks) the unused label column of `a1` and of `c1` is bit-identical to θ0's, while the used
column moves by up to 0.09 (`results/review_checks.json` → `zero_grad_label_column`). The claim
needs one qualifier: the label is a constant one-hot, so each label column only acts as a
per-task first-layer bias, 128 of 19,852 actor parameters (0.6%). Every other weight is shared.
A specialist gets no training signal for the other label, so it does no rehearsal, and forgetting
through the shared 99.4% is the expected outcome, not a surprise. "The task label does not protect
the other skill" is true, but the architecture gives the label almost no capacity to protect it with.

**Geometry** (actor parameters, `results/merge_s*.json` → `stats`): cos(τ_fwd, τ_bwd) grows with
branch length, from 0.07 at 125k to 0.21 at 2M (`pre`; 0.09 → 0.17 in `init`). |τ| / |θ0| grows
from 0.18 to 0.42 (`pre`) and 0.28 to 0.60 (`init`). The task vectors are nearly orthogonal and
large, yet still interfere.

## 3. Branch length: does merging work if the specialists branch only briefly?

`media/branch_length.png` shows absolute mean return over both tasks. In `pre`, every merge sits
on or below the θ0 line at every branch length (125k → 2M), while the oracle switch climbs from
3.7k to 6.7k. Short branches *look* better as a fraction of the specialist (task arithmetic retains
85% at 125k vs 38% at 2M). That is only because short-branch specialists have barely moved from
θ0. The TIES gain retained is 39% ± 37 at 125k (noisy, small denominators), then −5% to −10% from
250k on. In `init`, all merges stay at about 0 at every length.

## 4. Adaptation cost (how much work to get one network that does both)

Env steps until **both** tasks reach a fraction of the oracle switch, median over 4 seeds (first
eval at or above the threshold; "n/4" = seeds that reached it within the budget):

| start → method | 50% | 80% | 90% | at end of budget (fwd / bwd retained) |
|---|---|---|---|---|
| pre: θ0 → PPO multitask, 1M | 602k (4/4) | not reached | not reached | 58% / 78% |
| pre: average → PPO multitask, 1M | 651k (4/4) | not reached | not reached | 65% / 89% |
| pre: task-arith → PPO multitask, 1M | 303k (3/4) | 2/4 | not reached | 69% / 86% |
| pre: θ0 → **DAgger**, 200k | 29k | 53k | **53k (4/4)** | 99% / 100% |
| pre: average → **DAgger**, 200k | 29k | 29k | 29k (4/4) | 94% / 100% |
| init: θ0 → PPO multitask, 1M | 1/4 | not reached | not reached | 38% / 70% |
| init: average → PPO multitask, 1M | 303k (4/4) | 2/4 | not reached | 79% / 91% |
| init: task-arith → PPO multitask, 1M | 2/4 | not reached | not reached | 43% / 78% |
| init: θ0 → **DAgger**, 200k | 29k | 53k | **78k (4/4)** | 100% / 99% |
| init: average → **DAgger**, 200k | 29k | 29k | 29k (3/4) | 97% / 100% |
| random init → multitask PPO, 4.5M (= whole specialist budget) | 1128k | 3002k (3/4) | 2/4 | 85% / 101% |

* **Distillation is by far the cheapest way to combine the skills.** It reaches 90% on both tasks
  by the 53k (`pre`) or 78k (`init`) evaluation. No PPO fine-tune reached 90% within 1M steps (≥ 13–19×
  more steps, without getting there), and multitask PPO from scratch reached it in only 2 of 4
  seeds within 4.5M. The price: distillation needs both trained specialists as teachers (so 4–4.5M steps
  were already spent making them), plus teacher forward passes at every student step.
* *Review addition, total budgets:* specialists + DAgger ≈ 4.7M env steps (`pre`) → 99% / 100%,
  4/4 seeds ≥ 90% on both tasks. Multitask PPO from scratch, 4.5M → 85% / 101%, 2/4 seeds.
  Specialists + PPO fine-tune ≈ 5.5M → ≤ 78% mean retained, 0/4 seeds. At a matched total budget
  distillation still wins, by a modest margin. Merge-then-fine-tune is the worst use of the
  budget: it ends below multitask-from-scratch.
* *Review note on the medians:* a median over 4 seeds can fall between two eval points. 651k
  (pre average → PPO, 50%), 1128k (scratch, 50%) and 78k (init DAgger, 90%) are midpoints, not
  evals. Per-seed first-crossing steps are in `results/summary.json` → `adapt` and, for 90%, in
  `results/review_checks.json` → `steps_to_90_both_per_seed`. "First eval at or above" on a noisy
  10-episode curve is slightly optimistic for every method alike.
* **The averaged weights are a better PPO starting point than θ0,** although as a policy the
  average is worse than θ0 (`pre`) or useless (`init`). This is clearest in `init`: 85% vs 54% mean
  retained after 1M steps. Task arithmetic as a starting point is no better than the average in
  `pre` and worse and erratic in `init` (43% ± 39 fwd).
* Neither merge start reaches 90% on both tasks within 1M PPO steps. Forward running is always the
  laggard. The fwd specialist itself needed ~1M+ steps from θ0.

**Sequential transfer** (`pre`; PPO on one task, starting from the *other* specialist vs from θ0):

| target | start | at 0 | ~0.25M | ~0.5M | ~0.88M |
|---|---|---|---|---|---|
| bwd | fwd specialist | 897 ± 1111 | 4642 ± 415 | 5658 ± 404 | 6363 ± 230 |
| bwd | θ0 | 4797 ± 151 | 6126 ± 299 | 6724 ± 258 | 7307 ± 164 |
| fwd | bwd specialist | −552 ± 292 | 119 ± 145 | 519 ± 250 | 992 ± 397 |
| fwd | θ0 | 1643 ± 208 | 2481 ± 301 | 3155 ± 489 | 4287 ± 267 |

*Review caveat:* the "from θ0" rows are the specialists' own training curves, whose learning rate
anneals over 2M steps, while the transfer runs anneal over 1M. At 0.88M the transfer run's LR is
about 12% of the initial value, the specialist's about 56%. The schedules are not matched. The gap
(992 vs 4287) is too large for this to explain, but the comparison is not perfectly controlled.

Transfer is **negative** in both directions. It is strongly negative bwd → fwd: after 0.88M steps,
starting from the backward runner earns 23% of what starting from θ0 earns. The backward gait is a
deep, specific local optimum that PPO struggles to leave.

## 5. Scripted baseline

The open-loop CPG gait (`cpg.py`: 19 parameters, CEM on training seeds, one gait per task selected
by the label, `results/cpg.json`) scores **3676 fwd / 4372 bwd** on the eval seeds, which is 69% /
54% of the `pre` specialists (61% mean). On fwd it beats θ0 and every training-free merge
(≤ 1659). On bwd it beats the averaging floor (3358) and DARE but sits below θ0 (4797), task
arithmetic (4942) and TIES (5087). On mean retained it beats every merge (≤ 46%).
Tuning: f ∈ [0.5, 4] Hz, amplitudes [0, 1], phases [−π, π], offsets [−0.5, 0.5], CEM 40 iterations
× population 48, elite 8, and the final pick re-scored on 3 further training seeds. A tuned
sinusoid already runs forward at 3.7k. A merged network that scores below it on fwd has lost the
forward skill, not just some polish.

*Review re-tune (`cpg_wide.py` → `results/cpg_wide.json`, log `logs/review_cpg_wide.log`).* The
search above ended on its box edge: f = 4.0 Hz, the upper bound, for both tasks, and several
amplitudes sat at 1.0. The bwd elite mean was still rising at iteration 40. The re-tune widens the box to f ∈ [0.5, 8] Hz
(control Nyquist 10 Hz), A ∈ [0, 2] (with the clip this allows squarer waves) and b ∈ [−1, 1]. It runs CEM for
60 iterations × 48 with 2 restarts per task and picks the restart on 5 more training seeds (950–954).
Result: **fwd 4075 ± 43, bwd 4693 ± 59** on the eval seeds, 77% / 58% of the `pre` specialists,
**68% mean retained (was 61%)**. The picked frequencies (4.8 / 4.35 Hz) are now inside the box.
The search used 5.76M env steps per task, about 3× the original and more than one specialist's 2M
PPO steps, so this is a deliberately generous baseline. The conclusions hold and get stronger:
on fwd the CPG beats every merge by ≥ 2.4k, on bwd it is still below θ0 (4797) and the TA/TIES
merges, and on mean retained it beats every merge and the single-specialist network (56%).

## Compatible-pair follow-up (fwd vs low-energy cruise)

Is the negative result about merging itself, or about the conflict between fwd and bwd? I re-ran
the train + merge stages unchanged (`run_pair2.sh`, `SKILL_PAIR=fwd_cruise`, 4 seeds) on a
**compatible** pair: `fwd` (+v − 0.1|a|²) vs `cruise` (+v − 1.0|a|², low-energy forward running).
The source is `results/fwd_cruise/summary_fwd_cruise.md` and the plots are `media/*_fwd_cruise.png`.

* **With compatible skills and a pretrained shared start, merging does work.** The plain average
  keeps 76% of both specialists, 61% of what the branches learned after θ0, and clearly beats θ0
  (39%). The interpolation path `media/interpolation_fwd_cruise.png` (top left) is a smooth,
  monotone trade-off with **no barrier**. The fwd/bwd pair had a cliff on the same path.
* **Interference turns into synergy:** adding the cruise vector *raises* fwd return
  (θ0 + 0.5·τ_fwd: 4387 → with both: 5920). Likewise for cruise (2932 → 3514). cos(τ_fwd, τ_cruise)
  = 0.56 vs 0.21 for fwd/bwd.
* **Short branches merge almost losslessly:** average 96% and task arithmetic 99% at 125k-step
  branches. This falls to 76% at 2M as the branches drift apart.
* **But nothing beat simply using the cruise specialist for both tasks (86%).** A low-energy runner
  is still a decent sprinter (5091 = 72% of the fwd specialist). No merge beat the better of its
  two inputs, so "merging added a skill" is not shown even here.
  *Review check:* the cruise specialist is also the pick on validation seeds, under both selection
  criteria, in 3/4 seeds (`pre`, seed 2 picks fwd; still 86% ± 2) and in 4/4 seeds (`init`,
  where it keeps 91% ± 17 against 25% for the best merge). It also beats multitask PPO from
  scratch at 4.5M steps (86% / 75%, mean ≈ 80%) while costing 2.5M.
* TIES and DARE are *worse* than plain averaging on this pair. DARE's 90% drop-and-rescale
  destroys these small dense MLPs. A likely reason (not tested): with ~40k parameters and large,
  dense task vectors, the random-drop assumption from LLM fine-tunes does not hold.
* Without shared pretraining, the compatible pair still shows a loss barrier (both returns dip
  near α ≈ 0.6–0.7, bottom left) and merges keep only ~25%.

## What worked

* The setup itself. Two same-architecture specialists with identical conventions (frozen shared
  normalizer, task one-hot, same init) reach 5.3k / 8.0k, with an exact oracle-switch ceiling and a
  clean averaging floor, over 4 seeds at ~15 min of wall time.
* DAgger distillation as the "combine without retraining" method: one network, 99–100% of both
  skills, ~50k env steps, no rewards.
* Merged weights as an *initialization* for multitask PPO.

* Weight averaging / task arithmetic for the *compatible* pair (fwd vs cruise) with shared
  pretraining: 76% retained, no interpolation barrier, positive interaction between task vectors.

## What didn't

* Every training-free weight merge, in both conditions and at every branch length. With shared
  pretraining the best merge is θ0 itself. With a shared random init the merge drops the task label.
* Task vectors are not additive skills here: half a forward task vector already hurts forward running.
* Sequential transfer between the two skills: negative.
* TIES and DARE never beat plain averaging / task arithmetic. On the compatible pair they were much
  worse (49% and 7% vs 76%).
* Even on the compatible pair, no merge beat the better single specialist used for both tasks.
  *(Review: the same holds on fwd/bwd. The fwd specialist alone under both labels keeps 56%, and every merge ≤ 46%.)*

## Surprises

* The **validation search chose "no merge"** (λ → 0) once λ = 0 was allowed.
* **Pretraining did not make better specialists.** `init` specialists match or beat `pre` ones
  (5464 vs 5320 fwd, 7969 vs 8026 bwd). Pretraining only made merging *less bad*: θ0's shared basin
  keeps the merge near θ0 instead of collapsing to one direction.
* **Backward running scores higher than forward running** (8.0k vs 5.3k). Both directions use a
  normal upright gait, not a flip (see the demo). The asymmetry presumably comes from the cheetah's asymmetric leg geometry (not tested).
* Averaging in `init` gives a network that **ignores its task input**: in the interpolation sweep
  the fwd and bwd returns are mirror images at every α.
* A 19-parameter open-loop sinusoid beats every merge on forward running and on mean retained.
* PPO fine-tuning can *wreck* a good merged policy before improving it. On the compatible pair,
  one seed lost almost everything in the first 100k steps. Merge-then-RL needs a gentler start,
  e.g. critic warm-up, a lower learning rate or a KL anchor.

## Not measured

* Permutation alignment (e.g. weight matching) for the `init` condition: not measured. It would be
  the natural fix for "no shared basin".
* Low-rank (LoRA-style) specialist deltas trained as low-rank from the start: not measured. DARE
  and TIES are the only sparsification merges tested.
* Pure behaviour cloning without DAgger, and distillation with a smaller student: not measured.
* Merging more than two skills, and other bodies (Hopper, Walker2d): not measured.
* Fine-tune curves end at the last eval (0.9M of 1M steps; 4.25M of 4.5M for multitask scratch);
  the final ~0.1M steps of each fine-tune were not evaluated.
* Wall-clock numbers come from a heavily shared machine (load average 4–36). Not a clean speed benchmark.

## Next steps

1. Repeat the merge study with permutation alignment of the `init` specialists.
2. Constrain branches to stay mergeable: an L2 pull toward θ0 during specialization, or train only
   low-rank adapters per skill, then measure the capability vs mergeability trade-off.
3. Compare distillation and multitask training at a strictly matched *total* budget (including the
   specialists' cost). This is the "Go deeper" item.
   *(Review: partly done already. Specialists + DAgger ≈ 4.7M vs multitask-from-scratch 4.5M is in §4.
   A strict version would also count teacher forward passes and give PPO more seeds.)*
4. Extend the compatible-pair result to a 3-skill repertoire (sprint, cruise, jump). Check
   whether the merge ever beats the best single specialist when the skills are less redundant
   than fwd/cruise.

## Round 5: Add skills without erasing old ones

### TL;DR (Claude review, 2026-10-24; turn-2 numbers from three seeds)

The question: teach one HalfCheetah three speed skills, one at a time (forward +3 m/s, then
backward −3 m/s, then slow +1 m/s), and switch between them mid-run. Do the old skills survive?
Three ways were compared at the same training budget: small per-skill **adapters** on a frozen
shared network, **DAgger** (copy each new skill from a separately trained specialist "teacher",
replaying old examples), and **joint** PPO on all skills seen so far. A hand-written rhythmic gait
(**CPG**) is the classical baseline.

* **Turn 1 was under-budgeted.** Each method got 1.31M training credits and finished in about
  two minutes per seed. Forward and backward were never really learned (forward teacher
  validation tracking 0.08–0.16), so "the old skill was kept" meant little. The lesson: check
  that a skill was acquired before scoring whether it was retained.
* **Turn 2 (12× the budget, fixed PPO, a 0.70 teacher gate) works.** All three seeds passed the
  gate (teachers tracked 0.97–1.00 on validation). On fresh test starts, adapters, DAgger and the
  routed teachers ("oracle") all hold the commanded speed band **98% of the time**. Joint PPO
  manages **96%** with about 3× the speed error (0.19 vs 0.06 m/s).
* **Retention is no longer the hard part.** Adapters keep old skills exactly, which is guaranteed
  because their old weights are frozen. DAgger keeps ≥99.8%. Joint PPO's forward skill dips to
  92–94% while backward is being added, then recovers to 97–100%.
* **Switching separates the methods.** Over 144 mid-run switches per method (3 seeds × 48):
  joint **0** failures, DAgger **1**, oracle **2**, adapters **14**. The adapter failures cluster
  on one transition per seed. In seed 2, every one of its 8 backward→slow switches got stuck
  near 0 m/s. One likely reason: adapter routes (like the teachers) are trained only on their own
  skill, while DAgger and joint train with the command cycling every 200 steps, so they practise
  switching. This is a hypothesis and was not ablated.
* **Cost and memory differ more than accuracy.** Every learned arm is charged exactly 15,728,640
  credits (env steps + teacher queries, teacher training included). DAgger used fewer real env
  steps (11.5M) and gradient examples (115M vs 157M) and ran fastest (~1,090 s vs ~1,320 s joint,
  ~1,660 s adapters; machine shared). Deployed size: DAgger/joint 19,974 actor parameters,
  adapters 29,106 (+4,566 per skill), oracle 59,922 (three full networks). The **oracle needed only
  7.34M env steps** and matched the best method on everything. Distilling into one network buys
  a 3× smaller policy, not better control.
* **The CPG baseline was weaker than it should be.** The paired CPG (reused unchanged from turn 1)
  scores 0.80 ± 0.12 tracking with 51/144 switch failures, but this is mostly a bad search
  outcome on forward in seeds 0 and 1. In a reviewer check, the best of the three existing CPG
  searches was picked per skill on validation only (3× the per-seed search, 4.6M env steps, still
  under the learned arms' 15.7M). That CPG tracks **0.935** with **2/144** switch failures, as
  reliable at switching as DAgger and the oracle and better than adapters. The learned methods
  still lead on tracking (0.98 vs 0.935) and speed error (0.06 vs 0.25 m/s).
* **Caveats.** Only 4 test starts per seed, and HalfCheetah starts are nearly identical, so the
  144 switches are really 3 seeds × 6 transition types, repeated. Treat 0 vs 1 vs 2 failures as
  ties. Tracking (~0.97) is close to its ceiling, because the start-up acceleration counts as
  off-target. Turn-2 jobs took ~58 min per seed in two invocations, not one 45-min run (see
  "Runner notes"). Peak RSS was not measured.

### Turn 2 setup (Astra, written before the runs; unchanged)
