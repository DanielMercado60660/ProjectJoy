## Headline results (final pass)

**How to read "×NumPy".** NumPy is the baseline: fp32 on the CPU, run with `VECLIB_MAXIMUM_THREADS=4`
(the shelf's sharing rule; set on the launch command, not recorded in the JSONs). MLX CPU used the same
environment; Core ML's CPU path picks its own threads. A reviewer probe found the cap does **not** handicap
NumPy here: uncapped vs capped, NumPy took 416 vs 410 ms (e07 b=16), 16.3 vs 15.4 ms (e09 b=256),
36.1 vs 36.3 ms (e11 b=1000) and 1204 vs 1213 ms (e29 b=64), and MLX CPU moved by under 4% too

baseline is still a straightforward implementation (im2col convs, one BLAS call per layer, Python
between calls), not a tuned CPU engine; Core ML's CPU path is the strong CPU engine in this race.

## Finding 1: at batch 1, Core ML often runs on the CPU whatever compute unit you ask for

A provisional pilot run of event 09 saw identical batch-1 latency (0.055 ms) for AlphaZero on `coreml_cpu`, `coreml_gpu` and
`coreml_ane`. **That's real, and Core ML is not hiding it: its compute plan says every op goes to the CPU.**
Asking for `CPU_AND_GPU` or `CPU_AND_NE` only allows those units. The planner still picks the CPU when it
estimates the CPU is cheaper for that op at that shape, and for a 64-channel conv on a 6x7 board at
batch 1 it always does. The compute plan lists the GPU and Neural Engine as *supported* for every op
(`supported = CPU+GPU` / `CPU+NeuralEngine`); they are not *preferred*.

Evidence (`probe_coreml_batch1.py` -> `results/probes/coreml_batch1.json`; busy machine, load ~2.5,
interleaved timing, fp16 packages). Each cell shows median ms / device the plan prefers for every op /
process CPU-seconds per wall-second over back-to-back calls:

| model (batch) | params | coreml_cpu | coreml_gpu | coreml_ane |
|---|---|---|---|---|
| e09 AlphaZero 5x64 (1) | 0.37M | 0.054 / CPU / 1.25 | 0.053 / CPU / 1.25 | 0.054 / CPU / 1.25 |
| same layout, 128 ch, random weights (1) | 1.5M | 0.117 / CPU / 1.12 | 0.116 / CPU / 1.12 | 0.129 / **NE** / 0.49 |
| 256 ch (1) | 6.0M | 0.313 / CPU / 1.05 | 0.527 / **GPU** / 0.36 | 0.192 / **NE** / 0.32 |
| 512 ch (1) | 23.8M | 1.173 / CPU / 1.10 | 0.932 / **GPU** / 0.27 | 0.443 / **NE** / 0.16 |
| MLP 4096x4 (1) | 67M | 1.759 / CPU / 1.01 | 0.500 / **GPU** / 0.30 | 0.989 / **NE** / 0.08 |
| e09 AlphaZero 5x64 (256) | 0.37M | 3.815 / CPU / 1.00 | 0.508 / **GPU** / 0.58 | 0.796 / **NE** / 0.11 |

Four independent signs agree for the real e09 net at batch 1:
1. **Compute plan:** 43/43 ops prefer the CPU for all three compute units.
2. **Outputs are bit-identical** across the three units (max diff 0). Different hardware would round
   fp16 differently; as soon as the ANE takes over (128 ch) the outputs differ by ~1e-3.
3. **CPU time:** the process burns 1.25 CPU-seconds per wall-second on all three units. When the work
   really moves to the GPU or Neural Engine this drops to 0.08–0.58 (the CPU only waits).
4. **Timing distributions match:** p10/p50/p90/p99 = 0.052/0.055/0.059/0.07 ms on every unit (4000 calls each).

The crossover is per unit. The Neural Engine takes over first, at 128 channels (~1.5M params, ~60M MACs per
call). The GPU only takes over at 256 channels. At batch 256 every unit runs where you asked for this net. The same
pattern holds across the shelf (final pass, compute plans stored in `results/<event>.json`, batch 1):

| event | coreml_gpu at b=1 | coreml_ane at b=1 |
|---|---|---|
| 05_dungeon, 08_grand_prix, 09_alphazero, 11_physics_detective, 26_orchestra | all ops on CPU | all ops on CPU |
| 10_nca, 15_object_permanence, 29_image_gen | all ops on CPU | all ops on NE |
| 30_nanochat | all ops on CPU | 433/441 ops on NE |
| 07_terra (96x96 U-Net) | all ops on GPU | all ops on NE |

`coreml_gpu` falls back to the CPU at batch 1 in 9 of 10 events. It also stays on the CPU at the throughput batch in 05 (b=512) and 08 (b=256), and in 08 the ANE request stays on the CPU at b=256 too.

**Why the CPU path wins so big at batch 1** (final pass, e09: 0.054 ms vs NumPy 0.318 ms and MLX GPU 0.692 ms): this is
Core ML's own CPU backend, compiled once for a static shape and run with fp16 weights. The work is ~16M
MACs, so it needs ~0.3 TMAC/s, which fits the M5's CPU matrix units. NumPy pays for Python, im2col copies
and ~40 separate BLAS calls. MLX GPU pays a command-buffer round trip of about half a millisecond.

**How to read the leaderboard:**
- At batch 1, `coreml_gpu` and `coreml_ane` are often the `coreml_cpu` athlete under another name. They
  have the same speed and the same output. `make_report.py` marks them "fell back to CPU" whenever the plan
  put no op on the requested unit, colours them as Core ML CPU, and gives them **no medal**. Otherwise one
  engine could take gold, silver and bronze.
- "Core ML beats MLX at batch 1" is a statement about Core ML's CPU path, not the Neural Engine. It is
  still a real, usable result: for small nets at batch 1, Core ML on the CPU is the fastest engine on this
  Mac.
- To force the ANE or GPU for small models you would need batching, or a bigger per-call workload.
  Compute units alone don't do it.

## Finding 2: MLX GPU "fp32" matmuls are TF32 by default

Found independently by builders A (while building e11) and C (e30/e26), and measured here. With MLX
0.32.4 on the M5 Max, GPU matmuls with more than one row run with TF32-class precision by default:
relative error vs float64 is **~7–9e-4 for M >= 2** (1.6e-7 for M = 1, the gemv path; NumPy and MLX CPU
~2e-6). This explains an observation from that pilot run: MLX GPU disagreed with NumPy by ~1e-6 at batch 1 but ~0.01 at
batch 256, and MLX CPU agreed with NumPy, not with MLX GPU. The reference was the imprecise one. Setting
`MLX_ENABLE_TF32=0` gives true fp32 (rel err 5e-7). With it, e09 at batch 256 has NumPy within 8e-6 of MLX
GPU (was 0.0106), and e15 at batch 50 has NumPy within 1.6e-5 px (was 0.068 px).

MLX reads the variable once, at the first GPU matmul of the process. Setting it before that point works,
even after `import mlx`; setting it after a matmul has run has no effect. Harness consequences:
- `run_event.py --final` (and `--true-fp32` for dev runs) sets `MLX_ENABLE_TF32=0` before anything can run
  a matmul. Every run **measures** the mode (`mlx_gpu_matmul_rel_err`, `mlx_tf32` in the JSON), and
  `--final` aborts if the measurement says TF32.
- True-fp32 runs save the reference outputs to `results/refs/<event>_b<batch>.npz`.
  `run_event.py all --tf32-pass` then times MLX GPU with TF32 on, as extra athletes `mlx_gpu_tf32` and
  `mlx_gpu_compiled_tf32`, with agreement against those saved fp32 references. This pass runs in its own
  process, so it is not interleaved with the other athletes, and it runs no task checks.
  `make_report.py` merges these athletes into the event tables.
- Provisional JSONs written before this change used the TF32 reference. Their agreement numbers at
  throughput batches include up to ~1e-3 relative error from the reference itself. Builder A notes that
  e11's `qualifies` thresholds were set against the TF32 reference.

**Speed cost of true fp32** (TF32 pass vs scored pass, `results/summary.md`, "TF32 exhibition" table):
TF32 is 1.29–1.31× faster on the two big-matmul throughput races (26 b=2000, 30 b=256) and 1.11–1.12× on
11 b=1000. Everywhere else (all convolution events, every batch-1 race) the difference is within ±3%, which
is cross-process noise (e15 b=50 TF32 is 2% *slower*; 11 b=1 6–7% slower).

**TF32 athletes are exhibition only (reviewer decision).** `mlx_gpu_tf32` and `mlx_gpu_compiled_tf32` would
have taken 2 gold, 4 silver and 4 bronze. They get none: they were timed in a separate process (not
interleaved, so drift does not hit them alike), several of those podiums were decided by under 1.5% against
athletes in the other process, and they were judged by an error tolerance only, with no task check (the
task checks compare against the same process's `mlx_gpu`, which would be TF32 itself). The tolerance is
weaker than the task check: on 26 b=2000 the TF32 runs pass at hit-probability error 0.007 without a
pattern check, while coreml_cpu (0.013) fails the pattern check. The class-level crossover winner does not
change in any race when they are excluded (11 b=1000 goes to coreml_gpu, 26 b=2000 to mlx_gpu_compiled).

## Finding 3: MLX GPU at batch 1 loses to NumPy in 6 of 10 events
Final pass, e09 at batch 1: NumPy 0.318 ms, MLX CPU 0.391 ms, MLX GPU 0.692 ms (0.508 ms compiled).
Per-call dispatch and sync cost a few tenths of a millisecond, which dwarfs a 16M-MAC net. MLX GPU's batch-1
floor is ~0.16–0.3 ms even for the 1.6k-param 08 MLP (0.185 ms vs NumPy 0.0028 ms). It beats NumPy at
batch 1 only where NumPy's per-call work is large: 07 (14×), 29 (4.8×), 10 (2.2×), 30 (1.1×).

## What worked, what didn't (harness and report)
- `qualifies(agreement, task)` per athlete per batch (default "no tolerance defined"). The report
  awards medals only to qualifying athletes that ran where they asked to run.
- `--no-task`, `--batches`, `--out` keep smoke runs under 15 s and out of `results/`.
- `make_report.py` prefers final JSONs over provisional ones, labels which it used, and tolerates missing
  events. The demo page is validated by `tests/check_demo.js`, which runs every event x batch x filter view
  in node, and was checked in a browser at desktop and phone widths.
- The crossover chart uses params x batch and NumPy time as "per-call work". For convs, params x batch
  understates FLOPs, because weights are reused across positions. The NumPy-time panel is the better x-axis.

## Round 5: Benchmark the whole observation-to-action loop

**TL;DR for a real-time controller on this Mac (Claude review, 2026-10-24).**
- **At these rates every engine keeps up easily.** The car runs at 10 Hz (100 ms per frame) and the
  tracker at 30 Hz (33 ms). Every engine applies its action 1.2–3.3 ms after the frame
  (p99 ≤ 4.2 ms), with zero missed deadlines, zero dropped frames and 100% coverage. All 32/32
  car laps finish. For models this small, the model is not the bottleneck. Most of that delay is the
  loop around the model: sensor rendering takes 0.35–0.84 ms and picking up the finished result takes
  0.27–0.86 ms, while model compute takes 0.03–1.76 ms.
- **The engine shows up only faintly.** The tracker on Core ML CPU (median age 1.9 ms) has about
  2% lower pursuit error than on MLX GPU (3.3 ms): 3.740 vs 3.816 px. The reviewer checked that the
  cause is latency, not Core ML's fp16 model. Each engine's per-frame estimate is equally accurate
  (1.525–1.531 px), so the gap comes from how long the old estimate stays in force. The edge is
  consistent: Core ML CPU beats NumPy and MLX GPU in 8/8 nominal and 24/24 zero-delay stress matched
  conditions. It is still too small to matter. As in round 3, MLX GPU is the slowest loop at batch 1.
- **What matters is what happens when the controller can't keep up.** We injected a 50 ms service
  delay (a sleep, not a real engine) against the 33 ms frame period. Queueing every frame (FIFO) falls
  about 0.3 s behind. Acting on the newest frame instead halves pursuit error, from 20.30 to 10.18 px,
  and wins all 48/48 matched pairs over 6 seeds. It applies the same number of actions (1114 vs 1111
  of 1920). Latest drops 39% of frames; FIFO leaves 42% stranded in its queue when the episode ends.
  Rule: if service time can exceed the frame period, drop stale frames. Even so, latest is twice as
  bad as keeping up (10.18 vs 4.81 px), so the real fix is a loop that fits the period.
- **Reviewer corrections to the claims below.**
  - The "age predicts error, R² 0.925" result mostly reflects the experimental design. A bare
    delay×policy label predicts held-out seeds better (R² 0.937), and within any single condition age
    has negative held-out R².
  - "Rankings match round 3" holds for the tracker, where Core ML < NumPy < MLX GPU in 8/8 conditions
    at p50 and p95. It does not hold for the car: NumPy and both Core ML paths are tied within
    0.04 ms, and the exact round-3 order appears in 0/8 matched conditions at any percentile.
  - The "loaded" condition is a light GPU keep-alive (~1.2 TFLOP/s), not real contention. It does not
    show in the load average, and it made MLX faster.

  Evidence: [results/r5/review_r5_checks.txt](results/r5/review_r5_checks.txt) (from
  `review_r5_checks.py`).

*Reviewer correction (§4).* Astra's turn-2 text said "The result is not merely detecting the two
injected-delay levels." That is not supported. It is detecting the delay×policy manipulation:
- With no age at all, a four-level label for the delay×policy cell gets held-out-seed R²
  **0.937** for pursuit, higher than age's 0.925. Adding age to the label leaves R² at 0.937.
- 95.6% of pooled pursuit variance lies between the four cells.
- Within the 50 ms runs, a bare FIFO/latest label gets R² **0.835**, against age's 0.840. Age is
  high there because FIFO's queue is long; that explains why "age minus queue" has no predictive
  power.
- Within any single cell, age has negative held-out R² (−0.43 to −0.44) and cannot predict a new
  world's error.
- Seed-demeaning removes world difficulty but leaves the cell effect in place, so r = 0.9847 is
  also mostly design.

The age regression is therefore best read as a manipulation check: injected delay plus FIFO
produces old observations, and old observations produce error. "Compute time alone R² −0.008" is
correct but expected, since compute was not manipulated. The natural-variation evidence is the
within-seed, within-cell correlation. Engines with older observations do worse in the same world:
seed-demeaned r 0.95 in both zero-delay cells and 0.94 in 50 ms FIFO. This is consistent with the
numerics check above.

Within nominal worlds, age still correlates with small pursuit differences (**seed-demeaned
r = 0.9483**, slope **0.0481 px/ms**), but it cannot predict a new world's absolute difficulty:
held-out-seed R² is negative, including the six-seed zero-delay replication. For car lap
time, active age explains only **0.39%** of within-track variance (**r = 0.0628**); predicting
finish success is not estimable because every car succeeds. Model arithmetic, frame history
and world difficulty remain confounders; these correlations do not isolate age as the only cause.

*How realistic is "loaded"? (reviewer, §5).* Load is recorded per episode: the 1-minute load average
and power/thermal state before and after each episode, plus the count of background matmuls. The
added load is light. It runs about 570 matmuls/s of size 1024², roughly 1.2 TFLOP/s on a single GPU
stream, a small fraction of this GPU. It also does not register in the load average (nominal mean
1.23 loaded vs 1.38 ambient). The CPU engines barely notice it: matched active-age changes are
+0.02 to +0.05 ms for the car, and −0.02 to −0.24 ms for the tracker. A real concurrent training
job (large kernels, memory-bandwidth pressure, CPU threads) and CPU-side contention were **not
tested**. "Loaded" here means "the GPU is kept busy", which likely keeps it awake. Read the MLX
speed-up that way, not as evidence that contention helps. Ambient was not idle either: the 1-minute
load average was 2.90 at the first nominal episode and 0.67–2.90 across the nominal run.
